# Bayesian system identification by message passing

Code, data and results for the keynote at ERNSI 2026, the workshop of the
European Research Network on System Identification.

**Try it in the browser:** <https://wmkouw.github.io/ERNSI2026-talk/> — the
whole talk as one interactive notebook, nothing to install.

## The idea

The talk builds a model for one system in six steps. Each step starts from the
previous model, asks where it goes wrong on the data, and adds one piece to the
factor graph to fix that. Every piece is a reusable block, inference is local
message passing on the graph, and every model is scored by the same
one-step-ahead predictive density. Where a step helps and where it does not are
both measurements, not claims.

## The benchmark: a road bridge

`bridge.py` simulates a 30 m road bridge with one accelerometer. Two
structural modes, driven by traffic, wind and ambient tremor, and modulated by
things that are never measured: deck temperature, frost and damage. The
physics is simple on purpose, and it is not generated by any of the models
below, so none of them is exactly right. What makes it hard:

| property of the data             | why                                               | stage that answers it |
|----------------------------------|---------------------------------------------------|-----------------------|
| two modes                        | four AR poles                                     | 1. AR(4)              |
| natural frequencies drift        | stiffness depends on deck temperature             | 2–3. time-varying AR  |
| excitation spans 3 orders of magnitude | rush hour, storms, quiet nights             | 4. + HGF volatility   |
| abrupt regime changes            | frozen deck stiffens, damage softens              | 5–6. mixture of experts |

`data/sim_001.csv` is one five-day scenario at 20 Hz (72 000 samples), with
the simulator's ground truth next to the measurement: the true natural
frequencies, the implied AR(4) coefficients, the excitation intensity and the
regime labels. `python bridge.py` generates a new scenario and prints a
summary; it needs only NumPy.

## The model ladder

| stage | model            | what it adds                                           |
|-------|------------------|--------------------------------------------------------|
| 1     | AR               | static coefficients, exact normal-gamma update          |
| 2     | TVAR             | random-walk coefficients, drift rate fixed             |
| 3     | hier. TVAR       | drift rate inferred                                    |
| 4     | + HGF noise      | observation precision follows its own volatility chain |
| 5     | mixture          | a second expert (Matérn-1/2 GP), fixed switch          |
| 6     | Bayesian mixture | the switch learns its own Markov transitions           |

Two references sit outside the ladder: the Matérn-1/2 GP on its own (as a
state-space model, so inference is an exact Kalman filter), and a small causal
Transformer with a Gaussian head, trained once or retrained every night.

## Results

Day one is burn-in and hyperparameter selection; days two to five (57 596
samples) are scored, strictly one step ahead.

| stage | model                 | RMSE [mm/s²] | NLPD [nats] | 90% coverage |
|-------|-----------------------|-------------:|------------:|-------------:|
| 1     | AR                    | 30.0 | −2.081 | 0.963 |
| 2     | TVAR                  | 30.0 | −2.081 | 0.963 |
| 3     | hier. TVAR            | 50.2 | −2.784 | 0.928 |
| 4     | + HGF noise           | 34.6 | −3.620 | 0.887 |
| 5     | mixture               | 50.7 | −3.665 | 0.983 |
| 6     | Bayesian mixture      | 37.4 | −3.756 | 0.977 |
| –     | Matérn-1/2 GP alone   | 88.4 | −2.752 | 0.904 |
| –     | Transformer           | 57.2 | −3.109 | 0.865 |
| –     | Transformer (nightly) | 50.0 | −3.355 | 0.909 |

The predictive density improves at every stage; the point forecast does not.
An oracle given the true time-varying coefficients reaches an RMSE of
29.5 mm/s², so from stage 4 on the remaining gains are in the uncertainty, not
the mean. [`models/README.md`](models/README.md) goes through why each stage
behaves the way it does, what the Transformer is (and is not) telling us, and
four places where the textbook update does not work and what replaces it.

## Running it locally

Python 3 (tested with 3.12) with NumPy, SciPy, pandas, Plotly, Matplotlib and marimo. The
Transformer baseline also needs PyTorch.

```
pip install numpy scipy pandas plotly matplotlib marimo
marimo edit bridge_demo.py                      # the interactive notebook
```

The notebook has two parts. The first plays back a week of the scenario, with a
switch that reveals the hidden state of the bridge. The second shows the
results, and lets you point any of the models at any stretch of the trace and
watch its forecast against the signal at full rate.

To reproduce the results from scratch:

```
python -m models.run_all                        # fit all six, write results/
python -m models.transformer.run --nightly      # the baseline (pip install torch)
python -m models.decision                       # the closing decision example
python bridge_demo.py                           # redraw the slide figures
```

The models are plain NumPy, one folder per stage: `model.py` has the model,
`run.py` fits it. The shared blocks of the factor graph (coefficient chain,
noise precision, volatility chain, Matérn chain) are in `models/blocks.py`.

## Repository layout

```
bridge.py          the bridge simulator
bridge_viz.py      animation and plotting for the notebook
bridge_demo.py     the marimo notebook for the talk
data/              the five-day scenario used throughout
models/            the six stages, the two baselines, the shared blocks
results/           one-step-ahead forecasts and metrics per model, summary.csv
build_site.py      builds the in-browser version into site/
```

## The in-browser version

`python build_site.py` exports the notebook with marimo's WebAssembly export
into `site/`, bundling the simulator, models, data and stored results so the
page runs with no server. `.github/workflows/pages.yml` publishes it to GitHub
Pages on every push to `main`. Preview locally with
`python -m http.server -d site`; add `--mode edit` to the build to show the
code.
